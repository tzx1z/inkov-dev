InkVault

A password manager for your own XMPP server. Records are encrypted on the device by one Rust core shared by the web, Android and terminal clients. The server stores only ciphertext and delivers changes to the other devices within 1-2 seconds.

problem

Problem

Self-hosted password managers bring their own account system, API server and database, and each of them has to be deployed, updated and backed up. Many people and teams already run an XMPP server: it has accounts, authentication, a persistent connection that delivers changes, and federation between domains.

InkVault uses that server for storage and transport. The vault account is a JID, encrypted records live in the PEP nodes of the account, and no server code of its own is needed. The server must never see plaintext.

architecture

Architecture

All cryptography, the data model, conflict resolution and the sync engine live in one Rust library. The core does no networking: a client passes it the payloads received from the server and gets back the commands to send, so each platform keeps its own XMPP stack.

  • Web: TypeScript without a framework, the core compiled to WebAssembly, xmpp.js over WebSocket (wss://), sign-in by a FAST token after the first login
  • Android: Kotlin and Jetpack Compose, the core through UniFFI bindings, Smack over TLS, unlock by fingerprint through Android Keystore
  • Terminal: Rust with the core as a crate, tokio-xmpp over STARTTLS. An agent in the style of ssh-agent keeps the vault unlocked behind a unix socket
  • Server: Prosody 13 with pep, websocket, smacks and SASL2/FAST. Nodes are created with access_model = whitelist, so contacts with a presence subscription cannot read them

encryption

Encryption

The master password never leaves the device. Keys form a hierarchy, and only wrapped keys and ciphertext reach the server.

  • Argon2id with 64 MiB of memory, t = 3, p = 4. Parameters stored on the server are checked against bounds, so a server cannot weaken the derivation or make a device allocate gigabytes
  • Records are encrypted with XChaCha20-Poly1305. The AAD binds the ciphertext to vault_id, item_id and the key version: the server cannot swap one record for another or move it to a different vault
  • Changing the master password replaces only the salt and the user key wrapper. Vault keys, records and the local cache stay the same
  • The local cache is encrypted with a key derived from the vault key and opens only after unlock

sync

Sync

Every field, every tag and the deletion flag carry a hybrid logical clock (HLC) timestamp. A record is encrypted and published as a whole, the server keeps the last publication and sends it to the other devices of the account.

  • Merge is per field: the latest HLC timestamp wins, and a password that lost a concurrent edit stays in the password history. The merge is commutative, associative and idempotent, so devices converge to the same state
  • A new session downloads the whole node before publishing anything. A session resumed with XEP-0198 only receives notifications
  • Deletions are tombstones, not retracts: otherwise a device that was offline would bring a deleted record back. Emptying the trash replaces records with stubs that win any merge
  • If the server lost its data or was restored from an old backup, a device with a cache publishes the account and the records back

clients

Clients

The three clients share the vault format and the encrypted export format. The core, the Android and the terminal clients are open source under AGPL-3.0, the code of the web client is private. The screenshots use a test server and made-up data.

Terminal

stack

Stack

Core: Rust, RustCrypto (chacha20poly1305, argon2, hkdf), zeroize, serde, wasm-bindgen, UniFFI. Web: TypeScript, Vite, xmpp.js. Android: Kotlin, Jetpack Compose, Smack 4.5, BiometricPrompt, Android Keystore. Terminal: Rust, tokio-xmpp, rustls, clap. Server: Prosody 13.

role

My role

Author: designed the storage protocol on top of PEP, the key hierarchy and the sync engine, wrote the core, the three clients and their test suites.

result

Outcome

Version 0.2 of the core, the Android and the terminal clients is published: APKs signed by the author, static Linux binaries for x86_64 and aarch64, a crate on crates.io.

  • Property-based test of the merge: three devices with clocks up to 4 seconds apart, 20 000 random scenarios of edits, deletions, restores and syncs
  • Sync simulation: an in-memory PEP server and three devices with offline edits, broken sessions and delayed notifications, 5000 scenarios
  • End-to-end tests on a test Prosody: the web client passes 58 of 58 checks in Firefox, the terminal client 80 of 80, the Android client 25 of 25 on a Samsung Galaxy S23+
  • A search for test passwords and record names in the Prosody database finds nothing: the server stores only ciphertext
  • Test vectors give the same bytes in Rust, WebAssembly and Kotlin

Next: autofill on Android, OMEMO 2 to approve a new device from an existing one, and a storage component for sharing vaults between users, including users on other federated domains.
