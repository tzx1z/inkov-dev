how

Как InkVault работает с сервером

InkVault хранит записи на вашем XMPP-сервере через PEP (XEP-0163), стандартный механизм личных данных учетной записи. Записи шифруются на устройстве, сервер хранит только шифротекст и служебные поля: идентификатор записи и версию ключа. Отдельный сервер или база для InkVault не нужны.

Для сервера это значит следующее. Подключение устройства - самая затратная операция: сервер отдает все записи сразу. Сохранение - одна небольшая запись и одна транзакция в базе с записью на диск. Между подключениями устройство ничего не запрашивает, изменения приходят уведомлениями.

method

Как проверяли

Генератор нагрузки вел себя как клиенты InkVault: подключался к Prosody по XMPP с TLS, загружал хранилища, сохранял и читал записи. Размер и формат записей такие же, как у InkVault.

latency

Время ответа и нагрузка

До 180 операций в секунду время ответа почти не меняется. Дальше запросы начинают ждать друг друга, а при 260-280 операциях в секунду сервер выходит на предел: обрабатывать больше он не успевает, и растет только время ответа.

  • 37 мс99% запросов быстрее

  • не растетвремя ответа за 5 минут работы

load

Что нагружает сервер

Prosody обрабатывает запросы всех пользователей по одному, в одном потоке. Пока выполняется долгая операция, остальные запросы ждут.

Самая долгая операция - загрузка всего хранилища при подключении устройства. В тесте это 8% запросов, но половина времени работы сервера.

Время загрузки растет вместе с числом записей. Если поднять лимит до нескольких тысяч записей, каждое подключение такого пользователя будет задерживать весь сервер на секунды.

vps

Хватит ли ресурсов VPS

Расчет для VPS с 1 ядром, 1 ГиБ памяти и каналом 200 Мбит/с. 100 пользователей InkVault, у каждого 2-3 устройства, 10-30 подключений и около 5 сохранений в сутки, до 256 записей.

  • cpu

    Процессор: до 4 мин в сутки

    Сервер занят запросами InkVault от 30 секунд до 4 минут в сутки, меньше 0.3% времени. Второе ядро не нужно: Prosody работает в одном потоке.

  • memory

    Память: 250-400 МБ из 1 ГиБ

    Система 150-250 МБ, Prosody 30-60 МБ, кеш базы около 70 МБ. Свободно больше половины памяти.

  • disk

    Диск: база около 70 МБ

    2.8 КБ на запись вместе с индексами. Одно сохранение записывает на диск до 400 КБ: страницы базы и журнал транзакции. Для SSD при личном использовании это незначительный объем.

  • network

    Сеть: около 4 с после перезапуска

    В обычной работе InkVault использует доли процента канала. После перезапуска сервера 300 устройств загружают около 105 МБ, это около 4 секунд работы канала 200 Мбит/с.

  • restart

    После перезапуска: 7-22 с

    За это время все 300 устройств снова загружают хранилища. Сервер выполняет загрузки по очереди, поэтому в эти секунды он отвечает медленнее обычного. Для 500 пользователей это уже от 35 секунд до 2 минут.

  • users_100_500

overload

Что будет при перегрузке

В стресс-проверке сервер получал запросов в 10 раз больше, чем мог обработать.

  • 3000операций в секунду запрошено
  • 264операции в секунду обработано
  • 0ошибок и потерянных уведомлений
  • около 2 свремя ответа вместо миллисекунд

Сервер не завершился с ошибкой и не потерял данные: все запросы выполнены, все уведомления доставлены, ответы замедлились. После снижения нагрузки накопленная очередь обработана. Нагрузка личного сервера в сотни раз ниже этого уровня.

setup

Что проверить на сервере

Настройки в файле prosody.cfg.lua. После изменения перезапустите Prosody.

Хранилище SQLite

Выводы отчета относятся к хранилищу SQLite. По умолчанию Prosody хранит данные в файлах (internal), этот вариант не проверялся. Переключение на SQLite:

prosody.cfg.lua

storage = "sql"
sql = { driver = "SQLite3", database = "prosody.sqlite" }

Нужен пакет LuaDBI для SQLite, в Debian и Ubuntu это lua-dbi-sqlite3. Существующие данные переносятся утилитой prosody-migrator.

Лимит записей хранилища

Лимит задает pep_max_items. Значение по умолчанию 256 совпадает с лимитом хранилища InkVault по умолчанию. Если записей нужно больше, увеличьте лимит:

prosody.cfg.lua

pep_max_items = 10000

Модуль PEP

Модуль pep входит в стандартную конфигурацию Prosody и обычно уже включен в modules_enabled. Проверка проводилась на Prosody 13.0.7.

Скорость диска

Скорость сохранения зависит от того, как быстро диск подтверждает запись. Проверка для опытных пользователей, файл создается рядом с базой Prosody и удаляется после теста:

shell · fio

  1. fio --name=fsync --filename=/var/lib/prosody/fio-test --rw=write --bs=4k --size=16m --fsync=1 --ioengine=sync
  2. rm /var/lib/prosody/fio-test

Если в блоке sync percentiles значение 99.00th не больше 3000 usec, диск подходит.

Ограничение скорости

Если на сервере включено ограничение скорости подключений (модуль limits, например 10 КБ/с), первый импорт 256 записей займет около 50 секунд. Это работа ограничения, а не ошибка.

Резервная копия

Хранилище InkVault находится в базе Prosody. Копию можно сделать без остановки сервера:

shell · sqlite3

  1. sqlite3 /var/lib/prosody/prosody.sqlite ".backup '/var/backups/prosody.sqlite'"

Путь к базе зависит от установки.

database

SQLite и PostgreSQL

Все выводы отчета получены на стенде с SQLite и 100 пользователями. Для небольшого сервера SQLite достаточно.

PostgreSQL стоит выбрать для сервера на сотни пользователей и больше. В контрольном замере на этом же стенде с PostgreSQL сервер записывал на диск в 4-5 раз меньше на одно сохранение. Время ответа и нагрузка на процессор были близки к SQLite: Prosody выполняет запросы к любой базе по одному в своем потоке, поэтому на число запросов в секунду выбор базы влияет мало.
